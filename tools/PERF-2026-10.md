# Load performance, October 2026

Measured with `tools/perf/` (puppeteer-core and the installed Chrome, no extra dependencies). Branch `perf`, from `origin/main` at 2d2a77c.

## Method

Moto G class profile: 4x CPU slowdown, 1.6 Mbps down / 750 Kbps up / 150 ms RTT, 360x740 touch viewport, mobile user agent, cold cache (new browser context per run), median of 5 runs. A local server gzips text as GitHub Pages does. Google Fonts and the Cloudflare beacon are blocked so the numbers are the page's own cost and repeat.

```
node tools/perf/part-bytes.js                         # bytes per part, index.html raw and gzip, docs/parts/*
node tools/perf/measure.js "" premortem redteam learn --runs=5 --label=after [--docs=<folder>] [--fonts]
node tools/perf/smoke.js                              # every route as a deep link, section loading, failure and retry, core-to-section hand-offs
node --expose-internals tools/perf/deps.js name=partA.js,partB.js   # which names a group of parts shares with the rest
```

"Sidebar interactive" is when the first `route()` has finished: the script has run to its last line, so the sidebar's click handling and the first view exist. "Content" for a lazy route is the load event, which waits for its section files.

## Where the time goes

The page is download-bound, not CPU-bound. 760 KB of gzip at 1.6 Mbps is about 3.9 s, and the one inline script cannot run until it has all arrived. Script execution is 50 to 80 ms, total blocking time under 200 ms, first paint 0.6 s (the HTML streams and the CSS arrives first). So the lever is bytes in the main file.

Largest parts by raw size (full list: `node tools/perf/part-bytes.js`): partLearn 208 KB, partZ8.css 112, partS11 102, partEV 75, partRT 74, partCP 73, partDSA 63, partMX 61. JS is 2175 KB of the 2.6 MB file.

## What changed

Three sections, 518 KB raw, moved out of the single script into `docs/parts/<name>.js`, loaded once by an injected `<script>` the first time a route needs them:

- `learn.js`: partLearn (routes learn, redteamllm, redteamworld, glossary)
- `tsglossary.js`: partTSG (route tsglossary)
- `redteam.js`: partRT to partRT9 (route redteam), needs `learn`

How it works:

- `src/build-ws.js` has a `CHUNKS` table (name, routes, needs, parts). The core is the same part list minus those parts, plus `src/partLazy.js` (loader, loading card, retry) and `src/partZ19.css`. Files are written with `?v=<hash>` in the URL held by the core, so a changed section is never served from a stale cache.
- Sections are classic scripts, so they share bindings with the core only if the core is not inside a function. The public page's main script is therefore no longer wrapped in `(function(){ ... })()`. Checked in Chrome: no top-level name collides with a window property, and no section name is declared twice. Visible consequence: functions such as `goHash` are now globals; `tools/screenshots/capture.js` already prefers `goHash` when it exists (it did not before), and still works (checked with `premortem-report.png` and `tabletop-play.png`, `CAPTURE_NO_MIRROR=1 CAPTURE_PORT=8831`).
- The full bundle, `src/ts-workbench-v9.html`, is unchanged (wrapper and all parts inline). The suites read the parts themselves, so no coverage was lost. `src/test-chunks.js` (in `npm test`) checks that the main script and every section parse, hashes match, each section route is a loader stub, no declaration was lost or duplicated in the split, and the counts the All tools page shows before a section loads (`LAZY_COUNTS` in partLazy.js) match the data.
- Core code that reached into a section now loads it first, guarded by `typeof lazyEnsure === "function"` so the unsplit bundle behaves as before: `openSaved` (saved studio runs and exercises), "Start something new: Red team studio" in My workspace, the intro walkthrough (it uses Learn's modal), and "Do this in the studio" in a Learn guide. The saved-run summary in My workspace and the studio and T&S glossary cards on All tools no longer depend on the section being loaded.
- While a section downloads, the view shows a quiet "Loading this section" card that fades in after 200 ms; a failed download shows a retry button.

To add a section: add parts to `CHUNKS`, point its ROUTES entries at `lazyRoute` (the `routesFrom`/`routesTo` strings in build-ws.js), run `node --expose-internals tools/perf/deps.js` to see what the rest of the app takes from it, guard those, then `npm test` and `node tools/perf/smoke.js`.

Known edge: for the 10 minutes GitHub Pages lets a browser reuse an old `index.html` after a deploy, an old core can fetch a newer section file. Sections only use functions that long-lived parts define, so a mismatch is unlikely to matter, and a broken load shows the retry card.

## Left alone, and why

- Tabletop scenarios (partS1 to S13, 303 KB raw, about 101 KB gzip) and the metrics data (partMXd1 to 6, 98 KB): not split. `SCENARIOS` is read on every route (the sidebar count in `shellUpdate`), the home page, About, the command palette, demo mode, and the loop; `mxGloss`/`MX_GLOSS` feed the hover definitions in four other tools and are used at load time by partVD and partMAd. Splitting them means a generated index kept in the core plus edits at a dozen call sites, which is a behavior risk the numbers do not require yet. `deps.js` output for both is the starting point.
- Assessment tools (pre-mortem, coverage, maturity, COPPA, DSA, eval, AI assistants) stay inline, as asked.
- Font preload: not added. With fonts allowed (`--fonts`, real network), first contentful paint is about 100 ms later than with them blocked, because the Google Fonts stylesheet is render-blocking, and the Inter and Plex files then compete with the document for the 1.6 Mbps pipe (sidebar interactive 3686 against 3304 in separate 3 and 5 run medians). `display=swap` means text is never held for the font files, so a preload would add bandwidth contention, not remove a blocked paint. `preconnect` is already there.
- Cloudflare beacon: not deferred. It is already `defer`; parse and script cost is not visible in the numbers (script 50 to 80 ms), and moving it risks the analytics config (`spa: true`).
- The WebLLM sandbox (partRT9) was already on click: it is a dynamic `import()` of the library when the button is pressed, nothing downloads before.
- Minifying the inline script would cut more than anything left on this list; it needs a minifier in the build, which this change does not add.
