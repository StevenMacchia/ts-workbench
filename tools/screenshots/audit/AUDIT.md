# Workbench visual/UX audit

Captured from the built site at `http://localhost:8831` (docs/), desktop 1440×900 (viewport and full-page) and phone 390×844 (full-page), using `tools/screenshots/audit/capture-audit.js`. Screenshots live alongside this file as `<route>-<state>-<width>.png` (e.g. `coppa-report-1440-full.png`), plus `extra-*.png` for the palette, +New menu, tracker modal, a guided question screen, a toast, and dark mode.

**Capture-tool caveat (read before using the full-page PNGs):** Puppeteer's `fullPage` screenshot mode renders `position:sticky` and `position:fixed` elements (the left `.side` nav, the phone `.bnav` bottom bar) at the wrong vertical offset — they can appear to float mid-page or go missing, with a visible seam. This was verified against the live page (both desktop sticky-sidebar and phone fixed-bottom-nav stay correctly pinned on real scroll) and is **not a product bug** — it only affects the `-full.png` files. Ignore any apparent sidebar/bottom-nav misplacement in those files; trust the `-viewport.png` files and the live page for anything about sticky/fixed positioning.

Counts: **10 P1, 43 P2, 23 P3** (76 rows).

## Systemic — the five patterns behind most of the above

1. **Two "same action, different label" habits repeat across the whole tool set.** "Start over" vs. "Clear it and start yours" vs. "Clear example"; "Download" vs. "Download result" vs. "Download the roadmap"; "Copy" vs. "Copy link" vs. "Copy result" vs. "Copy report" — all for the same three or four underlying actions (discard example, download, copy/share). **Fix once:** define one copy constant per action (`START_OVER_LABEL`, `COPY_LINK_LABEL`, `DOWNLOAD_LABEL`) in `src/partD.js` next to `gradeOf`/`withUndo`, and have every tool's render function pull from it instead of hand-writing the string.

2. **The report header-action row isn't actually one shared component — every tool hand-rolls its own `<div class="...">` of buttons**, so COPPA/DSA got it right (one row, Edit/Save/Tracker/Download/Copy) while Coverage, Maturity and Vendors each diverge (actions split across multiple page locations, different primary button, actions hidden in example mode). **Fix once:** extract a `reportHeaderActions(opts)` helper in `partD.js` that every report tool calls with its own button list, so the row's order, the primary-button rule ("Download is always primary unless the tool overrides it on purpose"), and the example-mode visibility rule are enforced in one place instead of copy-pasted seven times.

3. **One pill component (`.sb-new`) carries three unrelated meanings** (status "WIP", status "New", feature tag "AI") with no color/shape differentiation, and the WIP status itself has three different text variants ("WIP" / "Work in progress"). **Fix once:** split into two components — a status-pill (color-coded, one fixed label per status) and a feature-tag pill (neutral, for "AI" only) — and standardize the WIP string to one constant used by sidebar, All-tools cards, and page headers alike.

4. **All-caps/letter-spaced labels are a leftover from an earlier pass, not the current style** — the app is sentence-case everywhere except the +New menu's "START FROM A TEMPLATE" and the overview's "FROM THE EXAMPLE COMPANY, PIXELRY:" banner. **Fix once:** grep for `text-transform:uppercase` / hand-typed all-caps strings in `partORG.js` and the overview banner and convert both to sentence case — there are only these two left.

5. **Long reference pages (both glossaries, the metrics one-pager) have no in-page navigation**, relying entirely on browser scroll over 6,000–14,000px of content with no sticky search bar, jump links, or back-to-top control. This is the same underlying gap (nothing to anchor a long scroll) showing up on every "big list" page in the app. **Fix once:** build one `stickyFilterBar()`/`sectionJumpLinks()` helper and apply it to the three long pages (`partLearn.js`'s glossary, `partTSG.js`, and `partMXd3.js`'s one-pager).
